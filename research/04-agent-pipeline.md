# 04 · Агентный пайплайн: роли человека, суб-агентов и CI

- **Предмет**: кто именно делает каждый шаг конвейера «корпус → книга»:
  человек, интерактивные суб-агенты pi или CI-агенты репо.
- **Источники**: `CONTEXT.md` (правила контента и issues),
  `.sandcastle/agent-workflows/` (набор workflow),
  `pi-subagents` README v0.84.0 (установлен 2025-11-01,
  `~/.pi/agent/packages/pi-subagents`),
  `pi-coding-agent/docs/extensions.md` (суб-агенты как расширение).
- **Вывод одной фразой**: решения и сшивание — за человеком в главной
  сессии; чтение корпуса и черновики секций — суб-агентам с изолированным
  контекстом; CI-агенты — никогда для контента.

## 1. Ограничение из устройства репо

В этом репо контент **не ходит через issues**: «Knowledge content is
authored in interactive sessions and committed directly» (`CONTEXT.md`);
label-workflows (`agent:implement`, `agent:review`, `agent:explore`, …)
обслуживают только код самого пайплайна. Значит, CI-агенты из
исследования книги исключаются — весь контентный конвейер живёт в
интерактивных сессиях + их суб-агентах.

## 2. Роли в контентном конвейере

| Шаг | Исполнитель | Почему |
|---|---|---|
| Хребет книги, оглавление, порядок глав | Человек + главная сессия | Это решения, их контекст живёт в сессии с автором |
| Чтение notes/постов по разделу, черновик кусков | Суб-агент (`worker`) | Изолированный контекст: тысячи строк корпуса не заливают главную сессию |
| Сшивание черновиков в главу, дедупликация | Главная сессия | Нужна память обо всей книге: сущности, перекрёстные ссылки |
| Проверка плотности/атрибуции | Суб-агент (`reviewer`) | Свежий взгляд без привычки к своему тексту |
| Второе мнение по спорной развилке | Суб-агент (`oracle`) | «Challenges assumptions without editing» (README pi-subagents) |
| Внешние факты (не из корпуса) | `researcher` + `evidence-auditor` | Требуют pi-web-access в дочерней сессии (README: prerequisites) |
| Индексация новых постов, таксономия | Человек-куратор | «agents propose, the curator decides» (`TAXONOMY.md`) |

## 3. Почему суб-агенты, а не «всё в одной сессии»

Изоляция контекста — не роскошь, а условие плотности: суб-агент,
получивший «собери факты по теме X из notes 004+009+010», возвращает
только результат с ID (map-шаг из `01-extraction.md`), и промежуточные
тысячи строк остаются в его сессии. Главная сессия держит в голове
оглавление, уже написанное и карту сущностей — ровно то, что нужно для
сшивания, и ничего лишнего. Это же снимает проблему компакции: длинное
чтение переживает суб-агент, а не главный контекст (ср.
`pi-coding-agent/docs/compaction.md`).

## 4. Типовой цикл «глава за сессию»

1. Выбрать раздел в `research/outline.md`; главная сессия выписывает
   темы таксономии и notes раздела.
2. Запустить суб-агентов (`worker`) на секции — каждому: список
   источников, правила плотности из `02-notes-to-book.md` п. 3,
   требование атрибуции ID.
3. Сшить результаты, устранить дубли, выстроить порядок.
4. `reviewer` проверяет: факт-на-абзац, атрибуция, «одно место на
   сущность».
5. Человек читает, правит формулировки, коммитит; карта главы
   дописывается в `outline.md`.

Шаги 2 и 4 параллелятся; шаг 3 — всегда один и в главной сессии.

## 5. Что не делегировать

- Решения хребта и порядка разделов (меняются только с автором).
- Правку таксономии и notes (кураторская зона по `TAXONOMY.md`).
- Финальную атрибуцию: суб-агент предлагает ID, человек/главная сессия
  перед коммитом выборочно проверяет возвратом к посту (правило
  «доверяй, но возвращайся к источнику» из `01-extraction.md`).
