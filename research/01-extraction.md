# 01 · Извлечение: как агенту читать большой корпус, не читая его целиком

- **Предмет**: приёмы извлечения знаний из корпуса постов агентом в
  интерактивной сессии.
- **Данные для проверки**: `data/normalized/*.jsonl` (2042 поста,
  ≈2,8 MB), `knowledge/index/posts.jsonl` (1278 записей),
  `knowledge/notes/001–013`.
- **Вывод одной фразой**: корпус никогда не читается подряд — маршрут
  всегда «индекс → выборка → посты → выжимка с ID», а готовые notes
  используются как кэш уже сделанного map-шага.

## 1. Почему «прочитать всё» — не вариант

Полный корпус ≈ 2,8 MB ≈ 0,7–1M токенов. Ограничения трёх уровней:

1. **Механическое**: инструмент чтения агента отдаёт до 50 KB за вызов —
   сплошное чтение корпуса это ~56 вызовов только на сырой текст
   (источник: лимиты инструмента `read` pi, doc
   `pi-coding-agent/docs`).
2. **Контекстное**: даже при вместимости, длинный контекст ухудшает
   внимание к деталям и вытесняет раннее (ср. механика компакции —
   `pi-coding-agent/docs/compaction.md`: сессия периодически сжимается,
   и «прочитанное когда-то» не переживает компакцию).
3. **Атрибуционное**: после сплошного чтения невозможно сказать, из
   какого поста взят факт — а для книги атрибуция обязательна.

## 2. Маршрут «индекс → выборка → посты → выжимка»

Индекс уже содержит то, что нужно для выборки: `source`,
`source_message_id`, `topics` (`knowledge/index/posts.jsonl`).

**Шаг 1 — сузить по теме.** Таксономия из 15 тем даёт срез, а не поиск:

```
strategies 416 · bot-architecture 302 · theory-of-markets 294 ·
latency-engineering 287 · exchanges 228 · infra 209 · microstructure 198 ·
risk 197 · people-community 158 · tools 138 · exchange-api 118 ·
market-data 118 · manipulations-algos 85 · pnl-reports 74 · toxic-flow 41
```

(замер по индексу от 2025-11-01). Тема главы известна из оглавления —
читаем только посты её тем.

**Шаг 2 — достать посты.** Индекс → `source_message_id` → точечное
чтение из `data/normalized/<source>.jsonl` по номеру строки/ID.
Важно: normalized-схема (`source, source_message_id, date, author, text,
forwarded_from, reply_to, …`) содержит дату и автора — цитата сразу
получает атрибуцию без дополнительных прыжков.

**Шаг 3 — выжимка с сохранением ID.** Правило: каждый факт в выжимке
несёт ID поста (`grisha#55`), как это уже сделано в notes
(например, `knowledge/notes/001`: «(grisha#55, grisha#66, grisha#67)»).
Выжимка без ID — мусор: её нельзя ни проверить, ни пересобрать.

## 3. Notes как кэш map-шага

Notes — уже выполненный map-reduce: например, `notes/001` (186 строк)
сжимает цикл grisha #54–#89 (36 постов) до таблиц и тезисов с
атрибуцией; `notes/003` (251 строка) — замеры MEXC из десятков постов.
Чтение note на порядок дешевле чтения исходников и **не теряет**
возможность вернуться к посту по ID.

Правило для агента: **сначала notes по теме, затем посты только для
закрытия дыр** (пробел, противоречие, нужна дословная цитата). Это же
правило делает работу агента дешёвой: глава собирается из ~10 notes +
десятка постов, а не из тысяч.

## 4. Точечный поиск вместо чтения

Когда тема размыта по корпусу, точечный `grep` по normalized-файлам
находит посты быстрее серии чтений. Проверено на живых данных: слово
«ликвид» встречается в notes/005 13 раз, в notes/001 — 6, в notes/008 —
2 — три note на одну сущность находятся одной командой без чтения
корпуса. По корпусу поиск стоит комбинировать с полем `topics` индекса:
grep даёт слова, таксономия — тему.

## 5. Что признать не работающим

- **Сплошное чтение канала подряд** — дорого, теряется атрибуция,
  результат хуже чтения notes + выборки (см. п. 1).
- **«Прочитай посты и напиши главу» одним промптом** — смешивает map и
  reduce: внимание модели делится между тысячами строк, глава выходит
  пересказом. Каждый шаг — отдельный вызов/суб-агент.
- **Чтение без цели** — без заранее известного раздела оглавления
  выборка не имеет критерия остановки (см. `02-notes-to-book.md`:
  outline-first).
